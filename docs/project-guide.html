BD Tax Assistant · Project Guide

What this project actually produces

A local-only tax-filing assistant for Bangladeshi individual taxpayers — and, underneath it, a production-shaped lesson in how RAG systems are really built. Seven phases, each with the user stories it exists to satisfy.

The one rule: it is a calculator with a librarian attached. The AI is only the voice.
Facts are versioned data · math is deterministic code · the model explains and retrieves, it never decides or computes.

THE OUTCOMEWhat you have when it is finished

Not a chatbot. A small desktop-local web app plus a set of command-line tools, where every taka on screen traces back to either a number you typed or a figure in a versioned rules file — and the model's only job is to put that into sentences you can read.

That output is the whole product thesis. Most side projects can't tell you whether they still work after a change. This one prints two numbers: does the math still reproduce a real filed return, and does search still find the right document. Everything in Phases 1 and 6 exists to make those two lines exist.

END TO ENDOne taxpayer, one filing season

The clearest way to see the outcome is to follow a single user through it. Rahim is a salaried resident individual who has filed once before. They are not a tax expert and do not want to become one.

  1. Phase 7 · intake Rahim opens the app in July and starts a draft for AY 2026-27.

    They paste in figures from their salary certificate. The app extracts candidates and asks them to confirm each one. Nothing enters the return until Rahim says yes. The draft is saved to a gitignored folder on their own disk — no NID, no TIN, just filenames pointing at their own documents.

  2. Phase 5 + Phase 1 · calculate The app computes the tax and shows the full working.

    Not just a final number — every line: gross salary, the exemption, the threshold, each slab band, the rebate and which of the three caps limited it. The working is the trust. A taxpayer who can follow the arithmetic believes the result; one shown only a total does not.

  3. Phase 5 · narration Underneath the table, it explains itself in plain Bangla or English.

    The model receives the finished breakdown as JSON and writes five sentences. It is forbidden from introducing any figure not already in that JSON. If it does, that is a bug — and a checkable one.

  4. Phase 4 · ask Rahim wonders whether their festival bonus counts. They switch to the Ask tab.

    Answer comes back with a citation — salary-income.md — which they can open and read. When they ask something out of scope ("what's the corporate tax rate?"), the app refuses without even calling the model, because retrieval scored too low. That refusal is a feature, not a gap.

  5. Phase 7 · planning They ask: would putting another 1,00,000 into DPS help?

    The app clones the draft, changes one input, and runs the same calculator again. It shows the tax delta beside the extra outlay — and if the 3%-of-income cap already binds, it says so plainly. No LLM does the math. "Spend more to save tax" is never a recommendation.

  6. Phase 6 · compare years Out of curiosity they run the same numbers through AY 2025-26 and 2026-27 side by side.

    The higher threshold looks like good news until the weaker rebate cap shows up — net effect is more tax. That conclusion comes from a config diff and two calculator runs, not from anything a model "knows".

  7. Phase 7 · filing coach The app prints a checklist and Rahim files manually on the NBR portal.

    Each confirmed value is mapped to the exact e-Return tab and field. Missing documents are listed. The app never logs in, never automates, never submits — NBR stays the system of record.

  8. Phase 1 · the loop closes After submission, Rahim copies NBR's confirmed result into private/returns/2026-27.json.

    That file becomes a permanent regression test. Next June, when the new Finance Act lands and the rules get updated, npm run eval proves that this year's return still reproduces exactly. The user's own tax history is the test suite.

THE BUILDSeven phases

Two thirds of the value is built before any AI appears. That is not a flaw in the plan — it is what production AI systems actually look like. Tutorials hide this ratio, which is why people who have done ten RAG tutorials still can't ship anything.

PHASE 1 Calculator & replay eval

eval passes no AI half a day THE GATE

Compute tax deterministically, then prove it correct by reproducing a return you actually filed. If the calculator can't reproduce a filed return, nothing built on top of it is worth anything.

User stories

  • As a taxpayer, I want to enter my salary and see my tax, so that I can check the figure my employer or accountant gave me.
  • As a taxpayer, I want to see every step of the arithmetic, so that I can believe the result instead of taking it on faith.
  • As the builder, I want to replay a return NBR already accepted, so that I know my rule figures are right without owning a copy of the Finance Act.
  • As the builder, I want ambiguous rules to be config switches, so that the eval settles them empirically instead of me guessing.
  • As the builder, I want a new tax year to be a new folder, so that adding AY 2027-28 costs zero code changes.

What gets built

  • rules/ay-<year>/config.json — thresholds, bands, rebate, minimum tax. Data, never code. Old years are never edited.
  • lib/calc/ — slabs, rebate (lowest-of-three + which cap bound), minimum tax, orchestration. Zero dependency on the AI layer.
  • eval/replay.ts — asserts every line of a filed return within 1 taka; prints the full working on failure.
  • eval/calc-cli.ts — npm run calc -- 2025-26
  • private/returns/ — your real filed returns. Gitignored, never embedded, never sent anywhere.
Done when npm run eval reproduces a filed return to the taka, and a failure names the specific line that diverged — which localises the bug to a config figure, not a code hunt.

PHASE 2 The corpus

complete no AI one afternoon

A small, clean, hand-curated body of markdown the Ask tab will retrieve from. About 12 files, 20–30 chunks. A small accurate corpus beats a large vague one — and Phase 6 lets you measure the difference.

User stories

  • As a taxpayer, I want plain-language explanations of the rules that apply to me, so that I understand why I owe what I owe.
  • As a taxpayer, I want answers scoped to my assessment year, so that a repealed slab never surfaces as current advice.
  • As a taxpayer, I want to be told when something is outside this tool's scope, so that I go to a professional instead of trusting a wrong answer.
  • As the builder, I want process content written first, so that I can test the whole pipeline before risking a single tax rate.

What gets built

  • rules/shared/corpus/ — year-independent process: registration, filing steps, payments, documents, source-tax verification, expenditure.
  • rules/ay-<year>/corpus/ — thresholds, slabs, rebate, salary income, house property, minimum tax, deadlines.
  • out-of-scope.md — gives retrieval something correct to return for questions the tool can't answer.
  • scripts/lint-corpus.ts — front-matter valid, headings present, sections 150–500 words.

Authoring rules that decide retrieval quality: one idea per ## heading · make the heading a question someone would ask · repeat context inside the chunk (it's retrieved alone) · numbers in prose are for explanation only — config.json always wins.

Done when every file has valid front-matter, one idea per heading, and npm run lint:corpus passes. PDF/OCR ingestion is explicitly out of scope — transcribe by hand.

PHASE 3 Indexing & search

not started embeddings (local) one evening

Turn the corpus into vectors in Postgres and search it from the terminal. Stop-and-stare phase: read raw similarity scores before wrapping anything in a UI. This is where the mental model locks in permanently.

User stories

  • As a taxpayer, I want to ask in my own words and still find the right rule, so that I don't have to know the official terminology.
  • As a taxpayer, I want my income figures to never leave my laptop, so that a free-tier provider can't train on my finances.
  • As the builder, I want to see the raw scores in a terminal, so that I learn what good and bad retrieval actually look like.
  • As the builder, I want to watch an unanswerable question still return five rows, so that I understand why a score floor is non-negotiable.

What gets built

  • Postgres 17 + pgvector (docker, port 5433) and Ollama running nomic-embed-text, 768 dims.
  • lib/rag/chunk.ts — split on ##, heading prepended to the body so it gets embedded too.
  • lib/rag/embed.ts — Ollama speaks the OpenAI wire format, so one SDK serves both providers.
  • lib/rag/search.ts — cosine search, year-filtered; shared chunks always included.
  • scripts/index-corpus.ts · scripts/search-cli.ts
Done when npm run search "…" returns a sensible top-5 with scores you believe, year filtering works, and you have personally watched an out-of-scope question return five rows scoring ~0.4. Cosine search always returns something — there is no "no results".

PHASE 4 Ask tab — retrieval + generation

not started retrieval + generation one evening

Answer rule questions from the corpus, with citations, and refuse what it doesn't know. There is no magic here: the prompt is assembled text. The model didn't know the answer — you handed it the paragraph and asked it to read.

User stories

  • As a taxpayer, I want to ask "is my festival bonus taxable?" and get a short answer, so that I don't have to read a manual.
  • As a taxpayer, I want every answer to cite the file it came from, so that I can verify it myself.
  • As a taxpayer, I want "how much do I owe?" to send me to the calculator, so that a language model never estimates my tax.
  • As a taxpayer, I want out-of-scope questions refused outright, so that I'm never handed a confident wrong answer.
  • As the builder, I want every question logged with its scores, so that a week of logs tells me which corpus file to write next.

What gets built

  • Guard 1 — score floor. If the best hit is under ~0.5, return a refusal and never call the model at all. Cheaper, faster, cannot hallucinate.
  • Guard 2 — prompt instruction. "Answer using ONLY the context. If it isn't there, say you don't know." Use both guards; this is what separates a demo from something usable.
  • app/api/ask — SSE streaming, citations sent first so sources render immediately.
  • A minimal UI — question box, year selector, streamed answer, citations list. Always render the citations.
Done when answers cite a source file, "how much do I owe" redirects to Calculate, and out-of-scope questions are refused without the model being called — verified in the log.

PHASE 5 Calculate tab & narration

not started narration only a weekend

A form that computes tax, shows the working, and explains it in plain language. The model receives finished numbers and writes sentences. A figure in the explanation that isn't in the breakdown is a bug.

User stories

  • As a taxpayer, I want a form laid out like the official e-Return, so that it feels familiar and I can transcribe straight across.
  • As a taxpayer, I want the calculation explained in Bangla or English, so that I actually understand it rather than just seeing a total.
  • As a taxpayer, I want to be told which rebate cap limited me, so that I know whether investing more would help at all.
  • As a taxpayer, I want unsupported income types rejected with a clear message, so that the app never quietly approximates my return.
  • As a taxpayer, I want to save a scenario and reload it, so that this year's work becomes next year's starting point — and a test case.

What gets built

  • app/api/calculate — validate → reject out-of-scope → computeTax(). Refusing is a feature.
  • app/api/explain — sends the Breakdown object, never the raw form. It contains no identifiers; keep it that way.
  • BreakdownTable — every line including per-band rows. Narration goes below the table, never instead of it.
  • Warnings + unverified banner + disclaimer — non-negotiable UI elements.
  • Scenarios saved in the same shape the replay eval reads.
Done when the narration contains no number absent from the breakdown, explains which rebate cap bound, and no identifier reaches the hosted model.
The check that matters: run identical inputs through both years and read the two explanations — if the model correctly says 2026-27 raised the threshold but weakened the rebate, and the net effect is higher tax, narration is working.

PHASE 6 Measurement, year tooling & polish

not started tooling a weekend

Make quality measurable and yearly updates routine. This is the phase most side projects skip, and the reason most of them can't be improved after they're built. Without measurement, every change is a guess.

User stories

  • As a taxpayer, I want a "what changed this year" page, so that I can see how the new Finance Act affects me.
  • As a taxpayer, I want the same inputs shown against two years side by side, so that I can see the real net effect rather than a headline.
  • As a taxpayer, I want the interface in Bangla, so that it's usable by the people who need it most.
  • As a taxpayer, I want to print the breakdown, so that I can carry it to the e-Return form.
  • As the builder, I want a hit-rate number, so that changing the chunker becomes engineering instead of vibes.

What gets built

  • eval/questions.json — ~20 hand-written cases, including refusal cases. A system that answers everything is broken in a way hit rate alone won't reveal.
  • eval/retrieval.ts — hit rate + refusal accuracy, wired into the same npm run eval.
  • scripts/config-diff.ts — year-over-year figure diff; becomes the change summary page for free.
  • The yearly ritual — ~2 hours, documented and rehearsed: copy folder, edit figures, re-index, re-eval, publish diff.
Done when npm run eval reports both replay and retrieval hit rate, refusal cases pass, and both assessment years still replay. Old years are never edited — that rule is what keeps the eval meaningful.

PHASE 7 Personal assistant & finance record

not started explanation only a weekend

Turn the calculator, corpus, and e-Return field map into a local filing workspace: collect evidence, prepare a draft, run rule-backed planning scenarios, guide manual submission. It does not submit a return. NBR remains the filing system, and its completed return remains the oracle for npm run eval.

User stories

  • As a taxpayer, I want to build my return over several sittings, so that I'm not re-typing figures each time I sit down.
  • As a taxpayer, I want a checklist of missing documents and fields, so that I don't get stuck halfway through the portal.
  • As a taxpayer, I want to know exactly which e-Return tab each value belongs in, so that manual entry is mechanical, not stressful.
  • As a taxpayer, I want to test "what if I put more into DPS?", so that I can plan before the year ends rather than discover it after.
  • As a taxpayer, I want lifestyle expenditure kept separate from deductions, so that I never mistake wealth reconciliation for a tax break.
  • As a taxpayer, I want my identifiers to never reach a prompt, a database, or version control, so that using this tool carries no privacy cost.
  • As the builder, I want the filed result transcribed by hand only, so that the eval can never be "made to pass" by the app's own guess.

What gets built

  • private/ay-<year>/return-draft.json — confirmed inputs + evidence filenames. Deliberately has no filed_result.
  • Confirm-before-use intake — the model may extract candidate values, but each must be labelled with its source and confirmed before reaching TaxInputs.
  • Planning scenarios — cloned inputs through the same computeTax(). Never an LLM for math. Base draft is immutable.
  • Filing coach — per-year checklist built from the portal field map: missing facts, required evidence, exact tab/field, source-tax items needing portal verification.
  • private/returns/<year>.json — after filing, transcribed from NBR. Closes the loop back to Phase 1.
The hard boundaries. The assistant must not: invent any value · write a filed_result from its own calculation · claim a benefit without a cited rule and a user-supplied amount · log into or automate the NBR portal · treat lifestyle expenditure as a deduction · recommend spending more to save tax. Local only — any future sync needs its own threat model first.

RATIONALEWhy the phases are in this order

Ordering ruleReason
Phase 1 first, alwaysIt's the gate. Pure logic, fully testable, no model uncertainty — and it settles the unverified rule figures empirically. A research problem becomes a test.
Phase 2 before Phase 3Indexing bad content teaches you nothing about retrieval. Curate first, so when retrieval is poor you know it's the retrieval, not the data.
Phase 3 before Phase 4Stare at raw similarity scores in a terminal before wrapping them in a UI. That's where the mental model locks in permanently.
Phase 5 after Phase 4Narration is the easiest AI step — it receives finished numbers and writes sentences. Do the hard retrieval work first.
Phase 6 before Phase 7Measurement has to exist before you build the workflow people will actually depend on.

BOUNDARIESScope, v1

In scope

  • Resident individual taxpayers
  • Salary income
  • House property income (net)
  • Bank interest
  • Investment rebate
  • Minimum tax
  • Lifestyle expenditure & wealth reconciliation

Out of scope — the app says so and stops

  • Business / professional income
  • Capital gains · foreign income · agricultural income
  • Non-resident taxpayers
  • Surcharge on net worth · company tax
  • Actual e-Return submission
  • Auth / multi-user / hosted deployment
  • PDF & OCR ingestion · bank syncing · portfolio advice
Refusing is a feature. Out-of-scope inputs should make the app stop, not guess. An assistant that answers everything is broken in a way no accuracy metric will show you.

REFERENCETerms used above

TermMeaning in this project
Assessment year (AY)The tax year the return belongs to, e.g. 2025-26. Each gets its own folder of rules and corpus. Old years are never edited.
Replay evalnpm run eval — feeds a return you really filed through the calculator and asserts every line within 1 taka. Empirical proof the rule figures are right.
CorpusHand-written markdown explaining the rules and the filing process. What the AI reads. It never supplies numbers to the calculator.
ChunkOne ## section of a corpus file, embedded on its own. Retrieved alone, without the file around it — so it must repeat its own context.
EmbeddingA list of ~768 numbers representing meaning. Two texts about the same thing land near each other even with no words in common.
Cosine searchFinds the chunks nearest the question in that number-space. It always returns rows — there is no "no results".
Score floorIf the best match is below ~0.5, refuse without calling the model. The single most important guard in the system.
RAGRetrieval-augmented generation. It does not teach the model your documents — it pastes relevant text into the question.
BreakdownThe labelled, line-by-line output of computeTax(). The only source of numbers the LLM is ever allowed to narrate.
rebate_bindingWhich of the three rebate caps actually limited you — income, investment, or the absolute ceiling. Turns a number into actionable advice with no model reasoning involved.
filed_resultNBR's confirmed result, transcribed by hand after filing. Evidence for the eval — never a prediction, never written by the app.
private/Gitignored. Your returns and drafts. Never committed, never embedded, never sent to a hosted model.
